> **本章命题**：序先立约，再指路。契约是那句总命题；路径可以分叉，命题不能分叉。「怎么读」是一张表，不是这本书的名字。

## 问题

点开一本写 Minecraft 的书，最容易以为会看到配方、版本年表，或「那些年我们一起挖的矿」。那些东西 Wiki 和附录已经写得更好。这里要回答的是另一件事：Minecraft 究竟是一种什么对象。

一句话先钉在这里，后文三卷都在证明它：

**Minecraft 不是通关即弃的内容，而是一套能住进去、能玩出设计之外、还能被再开发的系统。**

完整论证在下一篇（[《全书的命题》](/prelude/thesis)，十分钟够读）。本篇只做三件事：划清这本书不是什么、写给谁、按什么顺序进卷。路径表是第三节，不是开场白。

## 这本书不是什么

不是攻略。不教你过第一晚，会解释饥饿和黑夜到底在逼什么。

不是维基。能查到的事实会用，事实本身不是章节。章节问的是：为什么是这样，而不是别的。

不是怀旧散文。2011 年的口哨声、2013 年的服务器、某个世界存档——这些可以当材料。它们不能当结论。

不是控诉。Marketplace、双版本、聊天举报、收购，都会写。写成坏人故事最容易，也最没有用。真正值得写的是：一连串各自合理的决定，如何把一套可再开发的系统，推向另一种产品形态。

展开的口径——现象怎么开篇、判断怎样才算能被拆穿、Java 与 Bedrock 何时必须拆开——在[《体例与方法》](/prelude/method)。本篇只立约。立约之后，才谈跳哪一卷。

## 两类读者

**资深爱好者**要的是「原来如此」。你已经知道活塞能推、苦力怕会炸、创造模式能飞。你未必能说出：创造为什么不是关卡编辑器，服务器为什么才是很多人真正在玩的游戏，TPS 掉了的时候世界失去的为什么是因果而不是帧率。后文按这个标准写：把习以为常的东西变成可检验的机制。

**游戏开发者**要的是「可以拿走」。拿走的不是方块美术，是原则，以及——同等重要——**抄不走的条件**。没有不可迁移条件的原则是鸡汤。Minecraft 有过公开开发、付费 Alpha、二十年模组工具链、一整代人的影像入口。这些不是设计手法，是历史窗口。卷二末章会把两份清单分开写；在此之前，请把「我要做下一个 Minecraft」先搁下。

两类人读的不是同一本书的缩写。共用的是那句命题。分叉的是深度和顺序。

## 路径

不必按卷号通读。先读命题，再按下表跳。表里的「序」指命题加方法；本篇读完即可离开。

| 你更像 | 顺序 | 可跳过 |
|--------|------|--------|
| 设计师、玩法程序 | 命题 → [体素作为设计原语](/design/voxel-primitive) 起读卷二 → 卷一模组、服务器、影像与竞品 → 卷三技术债与卷结语 | 卷三实现细节 |
| 引擎、技术程序 | 命题 → 卷二体素与生存 → [体素世界的数据模型](/impl/data-model) 起读卷三 → 卷四 | 卷一影像章可略 |
| 制作人、商业 | [从 Infiniminer 到 Cave Game](/history/infiniminer) 起读卷一 → 卷二模组方法与可迁移原则 → 卷三双引擎与技术债 | 红石实现、渲染 |
| 资深玩家通读 | 按卷顺序；每章先读命题，再决定是否下沉 | 标了开发者侧重的章，可读命题与结尾 |

卷四是可选的重写思想实验，不是续作预告。没读过卷二原语和卷三结语就进卷四，会把尚未论证的「本质」当成前提。

作者侧的开工顺序——也是为什么设计原语会写在许多史实前面——是：原语 → 历史证据 → 实现约束 → 重写考试。不要从卷四起笔。阅读可以不照这个顺序；论证必须照。

## 为什么正文先写设计原语

「Minecraft 味」如果含糊着，后面每一句都会打滑。Beta 1.8 算不算「向游戏收敛」，取决于你认为生存是难度还是意义机器。红石的 bug 该不该修，取决于你认为「玩出设计之外」是设计还是事故。Bedrock 算不算「同一个游戏」，取决于度量衡是网格与动词，还是账号与跨平台。

这些判断的地板在卷二开头：体素、最小动词与手感、生存、四种模式。它们是不变量。后面所有「像不像 Minecraft」的句子，都要能指回这几章。所以即使你走商业路径或引擎路径，也建议先读这四章，再分叉。

方法篇把地板钉成纪律：现象开篇、证伪、双版本、不写什么。读完命题和方法，你应当知道这本书会怎样骗人、怎样被你拆穿。然后再把时间交给正编。

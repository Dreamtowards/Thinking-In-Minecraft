> **本章命题**：Minecraft 里最难保存的，不是那个程序，而是程序之上的世界、社会与二次创作——官方的保存能力止步于分发，其余部分靠玩家与社区自己。

## 问题

想象一个最常见的场面：有人翻出一块旧硬盘，里面有 2012 年的存档。那是他和三个同学第一次通宵挖矿的地方，有一座永远差一个屋顶的城堡。他想回去看看。

这个愿望会遇到三种命运。运气好，存档还在，而且那是 Java 版——几分钟就能装回当年的版本，站回那座烂尾城堡脚下。运气一般，存档没了：换电脑时格式化过，或者根本想不起放在哪。运气最差的一种，他想回去的不是单机世界，而是那台五个人一起玩的服务器——服务器早关了，世界文件躺在某台不再续费的出租主机上，多半已经被服务商抹掉了。

单机存档的命运至少握在玩家自己手里。服务器的命运握在服主的账单里，模组的命运握在作者和托管平台手里，版本本身的命运握在官方的分发架构里。所以本章的问题要从头问起：**保存 Minecraft，到底要保存什么？**版本、存档、服务器、模组，四类东西各难在哪一层？谁来保存它们？

这不是怀旧题。卷一走到这里，前面的章节已经把 Minecraft 讲成了一部媒介形成史：alpha 章讲它怎么边收钱边长出身体，服务器章讲它怎么长出社会，收购章讲它怎么变成 IP。媒介要成立，得有载体；载体会烂、会丢、会被注销。文化遗产这一章，清点的是这个媒介的物质基础还剩多少。

## 一个旧模组世界现在还打得开吗

先给结论：如果是 Java 版，大概率打得开，而且比绝大多数游戏容易得多。

官方启动器默认就能运行大多数历史版本；想再往前走，在设置里打开「历史版本」开关，连 1.0 之前的 Classic 和 Alpha 都能装回来[^launcher]。也就是说，「2013 年的世界配 2013 年的程序」这件事不需要任何第三方工具，官方界面里点几下就行。要注意的只有一条：官方建议把旧版本放进独立的游戏目录，并备份世界——旧版本不再获得支持，出了问题不会有补丁。

<Note>
「支持」在这里是个合同词：历史版本官方不修 bug、不保证安全，能玩是架构的副产品，玩起来什么样全看运气。
</Note>

Bedrock 版没有这样的后门。它通过各平台的应用商店分发，商店只上架最新版，手机端还会自动更新；主机上连手动选择版本的入口都没有。想装回一个旧版 Bedrock，基本没有正规渠道。这意味着 Bedrock 的旧存档即便还在，也很难找到能准确打开它的程序。两版存档互不兼容这件事，[《Java 与 Bedrock》](/history/java-bedrock)已经细说过，这里只补一句：Java 的旧世界有退路，Bedrock 的旧世界近乎没有。

好，现在把难度调高：那个 2012 年的存档是个模组世界。这时「打得开」要同时对上三层——当年的程序版本、当年的模组加载器（Forge 或别的）、当年的模组本身。整合包更麻烦些，它是把几十个模组和配置打包好的合集，任何一环消失，整包就凑不齐。程序这一层官方兜底；加载器这一层有社区归档；模组这一层最悬：作者弃坑、平台下架、没人接手维护，都会让一份存档变成「知道它需要什么、但再也凑不齐」的空壳。

世界文件本身还有一层隐蔽的损耗。新版本打开旧存档时，会自动把旧格式改写成新格式——这是单向的，旧版本读不了升级后的存档。生成算法也一样：旧世界里你已经走过的地块保持原样，没走过的部分会用新算法生成，于是一座 2012 年的世界，会在 2026 年的程序里长出风格断裂的新大陆。世界长什么样，取决于打开它的那个版本——这个事实是后面所有保存难题的缩影（技术上为什么如此，见[《存储与序列化》](/impl/storage)；改版本时怎么少弄坏东西，见[《兼容性策略》](/rewrite/compat)）。

<Memoir title="回归流程">

每年都有老玩家在论坛和 Reddit 上发同一个帖子：「我翻出了 2012 年的世界，还能玩吗？」回复区很快形成固定流程：先问 Java 还是 Bedrock，再问具体版本号，然后有人甩出启动器版本隔离的截图，有人提醒先备份，最后总有人问一句「你当年装了什么模组」。这套流程没有官方出处，却在十几年里被重复了成千上万次——它是社区替官方写的一份《旧存档抢救手册》。

</Memoir>

## 保存对象：版本、存档、服务器、模组

把「保存 Minecraft」拆开，其实是四件难度完全不同的事。

**版本：难在「有索引不等于有承诺」。**Java 版的分发架构里有一份公开的版本清单，启动器照着它回装任何历史版本——前面说过，这是副产品。副产品不可靠：2009 到 2011 年间的大量早期版本，官方从来没有完整保存过，它们散佚在世界各地的旧硬盘里。把它们一点点找回来的，是一个叫 Omniarchive 的社区项目：2017 年 9 月发起，靠联系当年的老玩家，已经找回了八十多个曾经失踪的官方版本[^omniarchive]。请注意这件事的责任结构——**官方的义务是让现在的人能玩，不是让过去的人能回来**。前者是合同，后者没有人认领。这个判断怎样才算错？如果哪天官方公开把「保存所有历史版本」当成工程来做，或者社区抢救彻底失败，两种情况都能推翻它。

**存档：难在「世界不是文件，是数据与算法的合谋」。**单机存档是四类对象里唯一完全由玩家自己保管的——一个文件夹，拷走就是保存。但同一份文件在不同版本里长出来的是不同的世界；世界和它的生成算法、数据包、模组耦合在一起。保存一个世界，严格说要保存「那份文件，加上能正确解释它的整套环境」。玩家语境里「存档」和「世界」是同义词；技术语境里，两者隔着一整套由程序版本和模组版本组合成的依赖关系。

**服务器：难在「它是社会，不是文件」。**一个服务器最值钱的部分从来不是世界文件，而是那群同时在线的人，是他们攒出来的经济、规则、地标和恩怨。文件可以拷，社会拷不走。服务器的死亡也最彻底：主机电费一停，一切蒸发。2023 年 5 月，曾长期位居全球最大的 Minecraft 服务器之列的 Mineplex 关闭[^mineplex]，它连一个官方世界归档都没有留下。绝大多数服务器的结局更安静：不续费，被服务商格式化，连讣告都没有。

服务器保存因此只有两种姿态。一种是临终保存：关闭前把完整世界打包发布，让任何人都能下载、单机参观——不少服主这么做。另一种是维持生命：继续付账单，让社会继续演化。那些运营了十年以上的老服务器是这个媒介真正的活遗产——不是因为里面的建筑多好看，而是因为它们证明了同一个世界可以承载十几年的公共生活。

<Alternative title="冻结，还是续命">

保存一个服务器，是在「博物馆」和「养老院」之间选。发布世界包是博物馆方案：世界定格，社会解散，任何人可以进去看，但没人住在里面。转手给接棒的社区是养老院方案：世界继续被住，但每一代人都会装修，几年后它已经不是原来那个世界。两个方案都不能真正「保存一个服务器」——因为服务器本来就不是那个世界文件。

</Alternative>

**模组：难在「版权分散、平台依赖、环境耦合」。**一个模组是作者的作品，挂在 CurseForge 或 Modrinth 这样的平台上；作者可以删除，平台可以下架。整合包引用几十上百个模组，任何一环消失，整包就残了。社区有镜像文化——下架前有人顺手存档——但镜像的版权状态是灰色的，没人能把它做成正经的公共事业。于是模组保存的现状也是自发的、私人的、无担保的。

四类对象摆在一起，就能看清为什么「官方不管保存」是结构性的，而不是 Mojang 或微软的疏忽：

<Constraint name="官方保存义务" verdict="凑合" chain="商业义务只对现在的玩家 → Java 靠启动器索引顺手保住旧版可玩 → Bedrock 把分发交给平台商店，副产品随之消失 → 保存始终是副产品，从来不是承诺">

这个结构有一个可观察的证据：Java 的保存能力来自启动器，而启动器服务的是「装哪个版本玩」这个眼下的需求；Bedrock 一旦把分发交给应用商店，「回装旧版」连作为副产品的资格都没有了。官方不是反对保存，而是保存不在任何人的考核表上。

</Constraint>

## 博物馆与研究

传统意义上的游戏文化遗产有一套成熟流程：博物馆收一台能跑的机器，配一段说明文字，讲清这款游戏的文化地位。Minecraft 在这套流程里已经有了位置：2020 年，美国 The Strong 国家游戏博物馆把它请进世界电子游戏名人堂[^hof]。

但名人堂奖的是「作品」，Minecraft 的麻烦恰恰在于它不只是作品。一座博物馆可以保存一台街机，却不知道怎么保存一个 Minecraft 服务器：保存哪个版本？保存世界文件还是聊天记录？保存建筑，还是保存那群人的十年？这些问题没有现成答案，因为博物馆的收藏单位是「物」，而 Minecraft 最有价值的部分是「过程」和「关系」。

研究界碰到的是同一个难题。关于 Minecraft 的学术研究覆盖游戏研究、教育学和机器学习多个方向，量级说一句就够：过去十年，把它当作可编程实验环境的项目，从课堂一直延伸到人工智能实验室。对研究者来说，它是一个可观察的小型数字社会标本——但这些研究记录的是快照，不是那个社会本身。

保存实践与研究之间，现状可以一句话概括：版本抢救有人做了（Omniarchive 这样半机构化的社区志愿项目），学术研究做了不少，而**服务器与模组的大规模归档，至今接近空白**。没有公共机构认领，没有稳定资金，只有玩家各自为政的私人备份。四类保存对象里，最没有着落的，恰恰是最难替代的。

## 品牌、审查、家庭友好 vs 创作自由

保存难题是本章的暗线，明线是一次治理冲突——它把「Minecraft 属于谁」这个问题摆上了台面。

背景先交代清楚。微软时代的 Minecraft 是一个面向全年龄的全球品牌，玩家里有大量未成年人。品牌管理在这里是一项正经业务：广告主要知道自己的内容出现在什么环境旁边，家长要知道孩子进的是什么样的空间。这不需要阴谋论——对一个孩子天天进出的平台，把安全做成默认设置，是标准的商业理性。

冲突发生在 2022 年。1.19 版本给每条 Java 版聊天消息附上一段密码学签名——可以理解为「证明这句话出自你这个账号」的暗号；2022 年 7 月 27 日发布的 1.19.1 补上了完整闭环：玩家可以在社交界面选中别人的消息，按类别举报，类别包括骚扰与霸凌、仇恨言论、恐怖主义与暴力极端主义等；被举报的消息经人工审核，属实者可被封禁联机和 Realms——后者是微软官方的订阅制小型服务器服务[^chat-report]。

官方侧的道理是清楚的。一个孩子在一个陌生人的服务器里被辱骂，他能找谁？以前的答案是找服主，而服主可能不管，或者本人就是骚扰源。平台级兜底是这类问题的标准解法，举报类别清单本身就是这份意图的陈述。

社区侧的道理同样清楚。Java 多人游戏十几年的治理传统是自治：服主定规则，封人踢人都在自己服务器里完成。举报系统绕开服主，直通平台；封禁落在微软账号上，等于平台对一个私人服务器里发生的事行使了终审权；而服务器想整体关闭这条通道，余地极小——服务端强制安全配置的开关在 1.19.1 里默认打开，想关得自己改配置，改完玩家连接时还会收到「此服务器未启用安全聊天」的警告。一位服主经营社区十年，规矩立了十年，一夜之间发现自己成了名义上的管理者：规则还在我手里，终审在你那里。

于是有了那个著名的社区回应：模组作者 Aizistral 发布了 No Chat Reports，把每条聊天消息上的签名直接拆掉，让消息无法被举报；从 1.19.1 起，它干脆禁用整个举报系统[^nocr]。大量服务器装上了它或同类插件，下载量五千多万。官方没有回撤这个功能，也实际上无法阻止服务器安装拆签名的模组。结果是僵持：官方渠道按官方规则治理，装了模组的服务器按自己的规则治理，两套规则并行至今。

<Constraint name="聊天举报的管辖权" verdict="待定" chain="平台要为未成年玩家兜底 → 兜底必须越过服务器自治 → 服务器以拆签名反制 → 平台规则与社区规则没有和解，只是划界共存">

这场冲突经常被讲成道德剧：一边是保护孩子的微软，一边是纵容毒化的私服；或者反过来，一边是粗暴的平台，一边是自由的社区。两种讲法都不成立。真实的分歧不在「该不该管坏行为」，而在**管辖权归谁**：同一句辱骂，由服主按本服规则处理，还是由平台按全球统一标准处理？未成年人保护是正当的，社区自治权也是正当的，两种正当性撞在一起，谁也没有获得决定性胜利。这个僵局本身就是答案的一部分：Minecraft 的治理层和它的内容层一样是多元共存的，而且没有总导演。

</Constraint>

顺带看清品牌管理的另一面。微软进场的这十年，收紧的从来不止聊天一处：用户协议限制过商用服务器的收费方式，品牌规范约束过周边与同人的边界。这些动作单看每件都有商业理由，合起来是一个方向：**IP 化之后的 Minecraft，需要它的公共形象可预期。**创作自由没有消失——模组、服务器、影像至今百花齐放——但它从「默认自由」变成了「边界内的自由」，而边界由品牌来画。这是收购章埋下的那条线，在本章走完了它的第一个十年。

## 卷一结语：卖的是可居住的媒介

卷一讲的是一部媒介形成史，现在可以把它收拢成一句话了。

Infiniminer 章里，它是一张被借鉴了玩法的原型图；alpha 章，它学会边收钱边生长；beta 与正式版，它靠口碑长成现象；模组章，玩家成为第二作者；服务器章，它长出社会；教育与影像章，它被挪用成别的媒介；收购与商业各章，它变成 IP、变成生意、变成一门被同行比较的品类。到本章，该说清这一切的物质后果了：**Minecraft 卖出去的从来不是一份程序拷贝，而是一种可居住的媒介。**

可居住，意味着它的价值不在软件里，而在软件之上的那些东西里。版本是它的地质层——每个玩家心里锚定着自己的地层；存档是私人记忆——那个 2012 年的烂尾城堡是真实的、独一份的；服务器是社会现场——一群人用十年证明了同一个世界装得下公共生活；模组是二次创作——媒介的生命力，用它长出了多少「别人的作品」来计量。四类对象都在，媒介就活着；四类对象若都散佚，只剩商标和授权商品，媒介就退化成了 IP。

所以本章命题的执行句是：**媒介一旦停止被再开发，就只剩 IP。**这不是修辞，是可以观察的过程：一个版本锁死、模组停摆、服务器清空的 Minecraft，和任何一个停服网游没有区别——程序还在，能玩，但没人住在里面了，它就从「一个地方」降格成「关于这个地方的照片」。

那么，谁来保存世界、模组与服务器？答案是：没有单一主体，也不该指望单一主体。官方保住分发的连续性，这是它的本分；社区志愿者抢救散佚的版本，这是他们的爱好；玩家备份自己的存档，服主决定世界文件的命运，模组作者和镜像者维持内容层的存续。保存 Minecraft 是一件没有作者的公共事务——和这个游戏的开发史一样，靠的不是计划，而是系统里长出来的自发秩序。这份秩序运转得并不算好：服务器归档接近空白，模组下架无声无息，Bedrock 的历史版本近乎保不住。它还在运转，只是因为还有人在乎。

卷二开始，问题从「这套媒介怎么长成的」换成「它凭什么能住人」：方块这个最小单元是怎么被选中的，挖掘与放置为什么手感如此重要，合成与背包如何组织欲望，一张由约束构成的规则网如何长出涌现。而如果你想先亲手摸一摸这一切的原点——启动器里就能装回 2009 年的版本，那是 Java 版留给所有人的一扇后门；至于重写者该如何系统地看见原作，卷四的[《看见原作》](/rewrite/seeing-the-original)会把它当成方法论来讲。

## 这一章留下什么

- **爱好者**：你硬盘里那份旧存档是这个媒介的原件之一，备份它的优先级不比备份照片低。
- **开发者**：能抄走的是「官方回装」的架构思路——公开版本清单加启动器索引，让旧版本可玩成为分发的副产品；抄不走的是 Omniarchive 式的社区抢救文化，它依赖一群闲不下来的老玩家。

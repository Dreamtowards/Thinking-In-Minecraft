写到这里，真正困难的事情反而是总结。前十三章已经谈过可修改世界、生存、库存、世界生成、生物、进度、建造、Creative、红石、命令、模组、多人和社区玩法；这些现象很容易让人继续追问：其中哪些只是 Minecraft 的具体做法，哪些才可能对新的沙盒世界仍然有参考价值？

问题在于，从“某种设计在 Minecraft 里长期有效”到“别的沙盒也应该这样做”，中间还有很长一段距离。方块有效，不等于所有沙盒都应该是一米格；Minecraft 没有技能树，不等于角色成长天然破坏沙盒；红石的历史怪癖能支撑大量机器，也不意味着新游戏应该主动制造一套难懂的怪癖。Terraria、Vintage Story、Enshrouded、Teardown、Roblox 等后来者之所以值得在卷一对照，正是因为它们继承了不同部分，也主动放弃了不同部分。[《竞争、模仿与产业影响》](/history/competition)

所以这一章不提供“下一款 Minecraft”的施工清单。

> **如果今天重新设计一个沙盒世界，我们真正应该继承的也许不是 Minecraft 的答案，而是它长期证明值得认真回答的一组问题，以及其中少数反复成立的关系。**

这些结论也只是卷二结束时的中间判断。卷三会继续检查它们在区块、Tick、网络、存档和模组架构里的实现代价；卷四则会更直接地问：哪些东西属于 Minecraft，哪些东西属于 2009 年以来那段无法重演的历史。

## 先区分：观察、关系与历史结果

很多设计讨论之所以越总结越自信，是因为把三种不同性质的东西写在了同一栏里。

| 类型 | 例子 | 可以直接迁移吗？ |
| --- | --- | --- |
| **对 Minecraft 的观察** | 大量世界状态可以被玩家长期修改；Creative 与 Survival 共用同一份世界表示 | 只能先确认事实，不能直接推出“别的游戏也应该这样” |
| **可能可迁移的设计关系** | 如果希望玩家长期经营同一世界，后期奖励最好不要让旧空间立即失去价值 | 可以参考，但需要说明目标和适用条件 |
| **历史与生态结果** | Java Modding、红石社区术语、十几年老存档、视频教程文化 | 很难在产品第一天“设计出来”，只能为其创造条件 |

旧稿里很多“原则”其实横跨三栏。比如“世界比引擎活得更久”，对于 Minecraft 的老存档和服务器是事实；对于一款每局二十分钟、主动赛季重置的沙盒竞技游戏，却可能根本不是目标。

因此，下面所有“值得继承”的判断都必须带条件。条件一拿掉，它们就会重新变成口号。

## 目前更值得带走的几种关系

### 第一件值得带走的，不是方块，而是世界可以成为玩法状态

卷二第一章真正重要的，不是立方体外观，而是**玩家的行动能够持续写回世界**。[《方块与可修改世界》](/design/modifiable-world)讨论过，挖掘、放置、地形改造和保存共同让环境不再只是战斗与移动发生的舞台。

#### 世界修改最好能够留下后果

如果玩家今天挖开的洞、修好的桥和建起的仓库明天仍然存在，这些行为就会进入之后的决策。路线改变了，资源位置改变了，基地功能也改变了。世界因此积累状态，而不是每次经过以后恢复成作者最初摆好的场景。

这对于长期沙盒尤其重要，因为玩家投入的时间可以转化成未来继续使用的基础设施。道路、农场、仓库、交通网和机器的价值，都来自它们不会在任务完成后立刻被系统收走。

但这不是“所有东西都必须可破坏”的原则。Enshrouded 的 Ancient Structures 会保留作者需要的不可修改区域，仍然可以同时拥有体素地形与建造；Teardown 则把可修改空间推向结构破坏，而不是采集和长期建设。[《竞争、模仿与产业影响》](/history/competition)

所以更可迁移的判断不是“世界必须完全属于玩家”，而是：

> **如果修改世界是核心玩法，就要明确哪些状态真正属于玩家、会保存多久，以及作者在哪些位置仍然保留更高权限。**

这是一条边界设计，而不是自由越多越好的价值排序。

### Progression 可以让玩家更强，也可以让整个世界更好用

Minecraft 当然有装备升级，但长期世界里更有意思的一种成长，是玩家逐渐降低自己已经遇到过的问题的成本。[《进度、维度与游戏后期》](/design/progression-dimensions)里，Elytra、Shulker Box、Beacon、Nether 交通和自动化基础设施都属于这种变化。

#### 后期奖励不一定需要让早期世界报废

很多线性 progression 通过不断更换区域和数值梯度制造前进感。新地图更难，新装备更强，旧区域逐渐只剩回忆。

长期沙盒可以选择另一种关系：新能力让玩家以更低成本重新使用旧世界。Elytra 没有删除曾经修过的基地，反而让基地之间更容易连接；Shulker Box 没有替换所有仓库，而是让物资在仓库与施工地点之间更容易移动。

这并不是反对等级、技能树或更强装备。Terraria 已经证明，更明确的 Boss 和装备 progression 完全可以和挖掘建造共存。真正需要先回答的是：**玩家应该不断离开旧内容，还是不断提高经营同一世界的能力？**

如果目标是后者，那么 progression 设计最好持续检查一件事：新的能力是在减少重复劳动，还是直接让旧空间、旧工具和旧工程失去意义。

#### 基础设施本身也可以成为成长

这也是道路、农场和自动化为什么在 Minecraft 后期会承担越来越大的 progression。玩家获得的不是一个永久写在角色面板上的 +20%，而是一条实际存在的铁路、一套机器或一个更好的仓库。

这种成长有一个独特的代价：它依赖世界持久性，也依赖玩家愿意维护空间。对于强调快速重开或短局竞技的游戏，它可能反而是负担。

因此，可以带走的不是“成长必须附着于物品”，而是更开放的问题：

> **玩家的成长究竟应该主要写在角色上、物品上，还是世界本身？不同载体会怎样改变死亡、交换、合作和长期价值？**

Minecraft 给出的只是其中一个很成功的答案。

### 可组合规则值得追求，但“简单”和“约束”都不是目的

旧稿曾经把“少规则”“约束即深度”“不真实物理”写得太像一组普遍规律。前十三章重新检查以后，可以留下的东西要更有限。

#### 真正有价值的是可观察、可推导和可组合

刷怪塔之所以能被工程化，不只是因为生成规则存在，而是玩家可以观察它、重复测试，再用空间改造影响结果。红石可以从门一路长成计算机，也不是因为元件数量少，而是信号、延迟、状态和机械响应之间存在相对稳定的因果。[《设计之外的玩法》](/design/emergent-play)

所以，比“规则必须简单”更值得继承的目标是：

- 玩家能观察到输入与结果之间的关系；
- 规则在相似条件下足够稳定，可以被反复验证；
- 不同系统之间存在真实交叉，而不是每个系统只在自己的界面里运行；
- 失败以后，玩家有机会判断哪里出了问题，而不是只能重新随机尝试。

简单规则通常更容易做到这些，但复杂系统也完全可能可读。Vintage Story 选择更密的地质、食物保存和工艺流程，同样可以形成深度，只是学习成本和节奏不同。[《竞争、模仿与产业影响》](/history/competition)

因此，“复杂”不是错误，“真实”也不是错误。真正需要问的是：复杂度有没有转化成新的判断和玩法，还是只增加了用户必须记住的例外。

#### 有价值的约束会改变决策，而不是只制造摩擦

SkyBlock 的资源稀缺很强，因为它迫使玩家重新理解每一份泥土、水和树苗；Adventure Mode 禁止随意破坏方块，可以让 Parkour 与谜题路线成立；Survival 的资源成本又会让建筑材料选择和施工方式产生差异。

这些限制之所以有价值，不是因为“更困难”，而是因为它们制造了新的决策。

相反，如果一个限制只要求多等十分钟、重复点击更多次，却没有改变任何计划，它不会因为是“约束”就自动变成深度。

所以旧《约束即深度》真正值得保留的，最终只有一个更克制的版本：

> **评价限制时，先问它是否让玩家需要重新判断、取舍或寻找替代方案；不要把摩擦本身当成设计价值。**

### 给玩家更高层的工具，但不必强迫所有创作使用同一种姿势

从逐块建造到 Structure Block、WorldEdit、Axiom、Bedrock Editor，再到 WorldPainter，第三部不断出现同一个问题：设计意图的尺度变大以后，最低层操作会不会变成纯重复劳动。[《创造模式与创作工具》](/design/creative-tools)

#### 操作粒度应该尽量接近当前的设计意图

如果作者正在决定一扇窗放哪，一块一块操作很自然；如果作者已经设计好一座塔楼，现在只想复制十次，继续逐块施工就不再提供新的判断。

因此，沙盒创作工具最好允许用户在多个尺度之间移动：方块、结构、选区、笔刷、地图级地形。不同层级不必互相取代，也不意味着最高层工具最“专业”、最低层最“纯粹”。

这一点同样适用于玩法扩展。Command、Data Pack、Add-On、Script、Plugin、Mod 并不是一条单向升级链；哪一层最合适，取决于作者此刻想表达的东西和作品怎样分发。[《命令、数据驱动与地图创作》](/design/commands-data-maps)

#### “造”和“玩”是否共用运行时，不必变成信仰

Minecraft 很有魅力的一点，是 Survival 施工、Creative 建造和实际游玩都能发生在同一个世界里。建筑不是先在 DCC 工具里做完再导入，而是玩家可以直接走进正在施工的地方。

这种连续性值得重视，却不必升格成“外部编辑器一定破坏沙盒”。大型地图和专业内容生产确实需要批量工具、离线处理和更强的编辑界面。

更值得继承的是：**工具切换以后，作品是否仍然容易回到实际玩法中验证。** 作者能否快速在宏观编辑和玩家视角之间往返，比坚持一种唯一正确的创作姿势更重要。

### 扩展性不是一个“支持 Mod”的复选框

Minecraft 的模组、服务器插件、地图、数据包和视频文化很容易让后来者得到一个表面结论：只要官方也提供 Mod API，就拥有同样的生态。

卷一已经说明这并不成立。Java Modding 的工具链、Bukkit / Spigot / Paper 服务器生态、教程和社区知识都是十多年积累的结果；Luanti 则提供了很好的反例——开放和可扩展可以被重新实现，但生态规模不会自动随 API 一起出现。[《竞争、模仿与产业影响》](/history/competition)

#### 真正值得设计的是扩展边界

产品仍然可以在第一天做出重要选择：哪些内容数据驱动、哪些事件可订阅、服务器能改到哪里、存档格式是否公开、创作者作品怎样分发、升级以后旧扩展怎样迁移。

这些选择决定了第三方作者未来能不能找到稳定落脚点。

但生态本身需要时间。工具要有人维护，知识要有人传播，接口要经过真实项目检验，一些原本没被当作 API 的行为还可能逐渐获得兼容成本。[《模组与玩法扩展》](/design/mods-expansion)

所以与其写“Modding 必须是一等公民”，不如保留一个更具体的问题：

> **哪些创作能力应该由官方稳定承诺，哪些适合交给第三方更深地修改？如果社区真的依赖了某个边缘行为，产品以后准备怎样处理这种事实上的接口？**

这比在第一版产品页上写“支持 Mod”困难得多。

### 多人设计真正变化的是信任范围

卷二多人章最后得到的结论，也不适合简化成“沙盒应该默认联机”。单人可以完整成立，而朋友 Realm、公共生存服和小游戏服务器其实是三种非常不同的产品环境。[《多人游戏与共同世界》](/design/multiplayer-world)

#### 同样的自由，在不同社区规模下会产生不同风险

十个朋友可以靠口头约定共享箱子和建筑；陌生人组成的公开服如果仍然完全依靠信任，很快就会遇到 grief、偷窃和权限争议。于是领地、日志、回档、管理员权限开始变得必要。

这里真正可迁移的关系是：**随着信任范围扩大，原本隐含的社会规则需要逐渐被工具化。**

这不意味着软件必须把所有伦理关系编码成权限。朋友之间“记得补种”“打龙等大家一起”这种约定完全可以保持在人际层；但当违规成本高到社区无法靠沟通承担时，系统就需要提供更明确的保护和恢复能力。

因此，多人沙盒在设计“多少玩家”之前，还应该问：玩家彼此认识吗？世界要保存多久？谁有恢复权限？资产价值有多高？离开和重新加入的成本是什么？

人数只是这些条件中的一个。

### 长期世界需要把兼容性看成玩家时间问题

这一点横跨卷一和卷二，也会直接进入卷三技术实现。

如果玩家能够在同一世界投入几年，那么更新影响的就不只是程序版本。它可能影响房子、机器、地图、服务器经济、Mod 和社区教程。卷一[《作为文化遗产的 Minecraft》](/history/heritage)讨论的正是这种积累最终为什么会获得保存价值。

#### 稳定并不等于永远不改

长期兼容很容易被写成“什么都不能动”。这同样过头。

游戏需要修复漏洞、提高性能、修改安全问题，也需要继续增加内容。某些旧行为即使有人使用，保留成本也可能远高于迁移价值。

真正需要改变的是评估方式：当一个行为已经被玩家写进大量作品以后，它就不再只是内部实现细节。修改它时需要至少知道谁会受影响、有没有替代路线、能否迁移，以及收益是否值得这次破坏。

这个判断适用于存档格式，也适用于红石时序、Mod API、命令格式和服务器插件接口。

所以如果一个新沙盒明确希望玩家长期居住，就应该尽早决定：

> **玩家的时间积累在产品升级中拥有多大优先级？**

答案可以不是“永远兼容”，但不能等十年后才第一次考虑。

## 哪些东西不应该被直接继承

到这里反而更需要列出一些**不能直接从 Minecraft 推成普遍原则**的东西。它们可能在 Minecraft 中工作得很好，却不构成新沙盒必须复制的答案。

### 一米方块不是可修改世界的唯一表示

Rising World 和 Enshrouded 已经说明，体素或可修改空间可以拥有更平滑、更细的视觉和建筑表达；Teardown 则证明体素也可以主要服务破坏和物理。[《竞争、模仿与产业影响》](/history/competition)

方格的价值在于可读、可编辑和容易组织，并不意味着所有新沙盒都应该坚持 Minecraft 的视觉粒度。

### 没有强主线也不是沙盒的必要条件

Terraria 拥有更明确的 Boss 和 progression，Enshrouded 则把可塑地形放进手工 RPG 世界。只要游戏明确知道自己希望玩家怎样前进，更强的作者目标完全可以成立。

Minecraft 值得借鉴的是“官方目标可以和玩家自定目标共存”的经验，而不是“任务越少越沙盒”。

### 角色成长不是天然敌人

Minecraft 大量成长附着在物品和世界设施上，这使交换、死亡和多人合作具有特殊效果。但 RPG 属性、职业和技能同样可以成为沙盒的一部分。

关键仍然是它们会不会让其他系统失去作用。如果一棵技能树让所有资源、建筑和地形只剩背景，那当然改变了游戏主语；如果角色成长和世界建设互相供给，它完全可能形成另一种成功结构。

### 不真实物理不是目标

格子水、悬浮石块和红石信号在 Minecraft 中非常有效，但“越不真实越好”没有依据。

Teardown 的结构物理、Vintage Story 更密的模拟都证明，更真实或更连续的系统可以产生自己的玩法。真正需要权衡的是模拟密度、可预测性、性能、学习成本和玩家能够采取的行动，而不是离现实多远。

### 历史怪癖不是应该主动制造的深度

Quasi-connectivity 现在有大量玩家依赖，因此修改需要考虑兼容；这不代表新系统应该故意设计一堆难以解释的边缘规则，希望十年后社区把它们研究成文化。

稳定使用会让怪癖获得历史价值，但历史价值只能经过使用积累，无法在设计文档里提前伪造。

### “买断、免费 Mod、分散社区”也不是唯一健康生态

Minecraft Java 的社区文化与其商业史密切相关；Roblox 则证明统一创作、分发和商业化平台也能形成巨大 UGC 生态。两条路线各有不同的权力关系和创作者成本。

因此商业模式和生态结构必须单独判断，不能因为 Minecraft 的某段历史成功，就把它写成所有沙盒产品的设计法则。

## 真正无法复制的，是已经发生过的历史

前面那些候选关系可以在新项目中重新考虑，Minecraft 还有一些东西根本不属于“设计原则”的范畴。

它们是时间积累出来的。

### 社区语言需要被使用以后才存在

“刷怪塔”“红石时钟”“SkyBlock”“Parkour”“Speedrun”不是开发者在 Alpha 阶段一次规划出来的完整词典。它们来自玩家实践、地图、Wiki、视频和服务器不断命名和传播。[《设计之外的玩法》](/design/emergent-play)

新游戏可以让系统更容易观察、分享和扩展，却不能提前指定哪一种误用会成为下一代人的公共语言。

### 兼容债也来自成功以后

老存档、旧 Mod、服务器插件、教程与版本习惯都会逐渐让某些规则变得很难修改。产品第一年如果没有人长期依赖，它们还只是实现；十年以后，它们可能已经变成玩家资产的一部分。

这类债务不值得浪漫化，但也不能假装它不存在。

### “Minecraft”这个名字本身已经是条件

卷一最重要的一个提醒，是后来者面对的已经不是 2009 年的空白市场。Minecraft 的方块视觉、YouTube 教程、学校使用、服务器文化和家庭认知都已经占据了一个非常强的公共位置。

今天做一款新的体素沙盒，玩家会带着 Minecraft 训练出来的预期进入；这本身就改变了设计条件。

因此，“为什么没有出现第二个 Minecraft”不能只用设计好坏解释。后来者不是在同一张起跑线上重复实验。

## 如果今天重新设计一个沙盒，更值得先问这些问题

与其复制一张原则清单，不如在项目开始时把几个真正会改变产品形状的问题问清楚。

| 问题 | 它实际决定什么 |
| --- | --- |
| **世界里哪些东西可以被玩家长期修改？** | 作者控制、玩家所有权、存档价值、关卡设计边界 |
| **玩家的成长主要写在哪里？** | 角色、物品、基地、交通、自动化之间的权重 |
| **规则怎样被观察和推导？** | 学习成本、社区教程、系统组合与工程玩法 |
| **创作需要哪些操作尺度？** | 逐块建造、结构复用、选区、笔刷、地图级编辑之间的工具分工 |
| **官方准备稳定开放哪些扩展层？** | 地图、脚本、插件、Mod 的部署与兼容边界 |
| **多人世界依赖多少信任？** | 财产、权限、回档、管理员与社区规则 |
| **一个世界预计活多久？** | 版本兼容、存档迁移、赛季重置与内容更新策略 |
| **官方目标和玩家目标怎样共存？** | progression、探索、长期自定目标之间的张力 |

这些问题没有 Minecraft 标准答案。

但只要答案彼此一致，新的沙盒就不需要长得像 Minecraft。一个世界可以更真实，可以拥有强主线，可以把建造交给专业编辑器，也可以以赛季为生命周期；关键是这些选择是否共同服务于同一种玩家关系，而不是因为“沙盒应该有”就把互相冲突的系统全部塞进去。

## 卷二到这里真正完成了什么

卷二没有证明 Minecraft 存在一套不可替代的设计本质。

它做的事情更有限：把一个已经运行十几年的沙盒拆成若干关系，观察它们怎样互相影响，再用后来者、版本差异和社区实践不断削弱那些过于漂亮的结论。

目前最值得继续带进卷三和卷四的，不是一套数字编号的原则，而是几组仍然反复出现的关系：

- **玩家修改世界的能力，只有和保存、资源、建造与后续使用连接起来，才会形成长期意义。**
- **Progression 可以升级角色，也可以升级物品和整个世界；选择哪一种，会决定旧内容是否持续有价值。**
- **系统是否可观察、稳定和可组合，比规则数量少不少、物理真不真实更值得单独检查。**
- **创作和扩展需要多种尺度与不同接口；工具选择应该接近设计意图和部署环境。**
- **多人自由会随着信任范围变化而产生不同的保护需求，社会规则本身会进入玩法。**
- **如果世界和作品预计长期存在，兼容性就不仅是工程成本，也是对玩家时间投入的处理方式。**
- **社区能够继续设计游戏，但社区玩法不会自动发生；规则、实践和传播共同决定哪些可能最终成为文化。**

这些判断都还有反例，也都可能在后面的技术和 Reinvention 中被改写。

这恰好是它们现在应该保持的状态。

如果一本关于 Minecraft 设计的书在第二卷结束时已经能够宣布“下一款沙盒应该怎么做”，那更可能说明我们总结得太快，而不是理解得足够深。

卷三接下来会换一个问题。不是“为什么这样设计”，而是：**这样一个可以持续修改、生成、联机、扩展并保存多年的世界，在技术上究竟怎样才能运行？**

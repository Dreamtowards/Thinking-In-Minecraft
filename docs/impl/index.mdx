卷二讨论 Minecraft 的设计规则为什么会形成今天的玩法；卷三切换视角：**这些规则怎样被做成一个可以保存、持续模拟、跨网络同步，并运行十多年的软件系统？**

一个近乎无限、可随时修改、还要兼容旧世界的体素世界，需要怎样的数据结构、调度策略和运行时工作集？哪些实现是体素沙盒的共性问题，哪些是 Minecraft 演化过程中的具体特性？

## 六个部分

### Part 1: 世界与数据

**核心问题**：世界在内存、磁盘和生成规则中分别是什么？

从方块状态、区块存储、版本迁移到世界生成，这一部分建立 Minecraft 数据模型的基础。重点不是枚举所有方块属性，而是理解一个可扩展、可持久化的体素世界怎样组织数据。

### Part 2: 世界如何运行

**核心问题**：离散时间步进和局部规则怎样让巨大世界持续变化？

从 Tick 循环进入方块更新、光照、流体、实体、物品和红石。这里关心的是运行时模拟的边界：什么会被 Tick、什么会被跳过、谁决定更新顺序。

### Part 3: 客户端、网络与性能

**核心问题**：世界怎样变成画面，又怎样在 Client-Server 间保持一致？

渲染管线、网络同步、区块流送和性能分析。这一部分的核心是"分布式世界"：客户端看到什么、服务器模拟什么、两者怎样通过协议保持一致，以及兴趣管理怎样把无限世界缩成可运行的工作集。

### Part 4: 扩展与服务器生态

**核心问题**：数据包、Mod、Plugin 分别在哪一层扩展 Minecraft？

从数据驱动、Mod 加载器到服务端软件，讨论三层扩展面：数据层（不改代码）、Mod 层（深入引擎）、插件层（服务端规则）。重点不是"能不能改"，而是版本边界、运行时所有权和长期维护成本。

### Part 5: 两种实现与长期演化

**核心问题**：Java 版和 Bedrock 的选择带来了什么？兼容成本从何而来？

Java 运行时、Bedrock 的另一套实现、兼容与技术债。这一部分把前面的机制放回十多年产品历史中，说明哪些"债"其实是"资产"，哪些约束无法通过重写消除。

### Part 6: 扩展的极限

**核心问题**：社区 Mod 怎样突破 Minecraft 的核心约束？

机械动力让方块可以移动，航空学让体素结构可以飞行，Distant Horizons 突破了渲染距离。这些 Mod 不是"加内容"，而是"重写引擎"。这一部分通过具体案例展示 Mod 生态的极限，以及为什么官方不采纳这些设计。

## 怎么读这一卷

**爱好者**：每章从玩家可观察的现象进入，再下到实现。不需要记住类名和版本细节，理解"为什么这样分层""为什么不能混成一个状态"就能接住主线。

**开发者**：类名和数据结构是证据，不是答案。重点是理解这些实现试图解决的约束，以及修改它们需要付出的兼容成本。具体实现会变，但约束和权衡的模式值得迁移。

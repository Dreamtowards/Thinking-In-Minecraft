卷二讨论 Minecraft 的规则为什么会形成今天的玩法；卷三换一个角度：**这些规则怎样被真正做成一个可以保存、持续模拟、跨网络同步，并运行十多年的软件系统？**

这里不会把 Minecraft 当成一份值得逐类抄写的源码。更重要的问题是：一个近乎无限、可以随时修改、还要兼容旧世界和社区扩展的世界，需要怎样的数据边界、调度方式与运行时工作集？哪些实现是体素沙盒普遍会遇到的问题，哪些又只是 Java Edition 多年演化留下的具体答案？

## 五部主线与一个专题

**第一部 · 世界与数据。** 从[《体素世界的数据模型》](/impl/data-model)开始，讨论 Block State、Chunk / Section、存档与版本迁移，再进入世界生成。这里回答的是：世界在内存、磁盘和生成规则中分别是什么。

**第二部 · 世界如何运行。** 从[《游戏循环、Tick 与调度》](/impl/tick)进入方块更新、光照与流体、Entity、Item 与 Redstone。重点不是罗列 Tick 类型，而是看离散时间和局部规则怎样让一个巨大世界持续变化。

**第三部 · 客户端、网络与性能。** [《客户端渲染与反馈》](/impl/client-rendering)讨论世界怎样变成画面与声音，[《网络架构与状态同步》](/impl/networking)讨论共享世界怎样跨 Client / Server 保持一致，[《区块生命周期与世界流送》](/impl/chunk-streaming)则把近乎无限的世界缩成一个不断移动的运行时工作集。最后再统一讨论性能预算、Profiling 与优化。

**第四部 · 扩展与服务器生态。** 数据驱动、Java Mod、Mixin、Loader、Plugin 与大型服务器分别提供不同层级的扩展面。这里关心的不只是“能不能改”，还包括版本边界、运行时所有权与长期维护成本。

**第五部 · 平台、兼容与长期演化。** Java / JVM、Bedrock 的另一套实现、兼容与技术债最终把前面的机制放回十多年产品历史中，并在《技术实现留下了什么》中收束卷三主线。

**扩展的极限**是一个可选专题。它不承担前五部的线性知识主线，而通过 Create、Valkyrien Skies、Voxy 这类系统级 Mod，观察社区在取得代码级扩展能力以后，究竟能把 Minecraft 原有的机械、空间、物理、世界表示与渲染边界推到哪里。

## 怎么读这卷

这一卷主要面向开发者，但每章都尽量先从玩家可以观察到的现象进入，再下到实现。爱好者不需要记住类名和当前版本的具体常数；理解“为什么要分层、为什么这些状态不能混成一个状态”就足以接住主线。

对开发者来说，类名和数据结构则是证据而不是答案。Java 26.3 今天使用的 Ticket Level、ChunkStatus、Data Component 或 Wire Evaluator 都可能继续变化；真正值得比较的是它们试图解决的约束，以及修改这些实现时需要付出的兼容成本。
